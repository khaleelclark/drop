# Installed desktop client

The Tauri 2 shell bundles `web/dist`; a Rust transfer worker owns file bytes, HTTP and persisted queue state. It stays resident when its window closes. The tray/menu offers **Open Zing** and **Pause transfers and Quit Zing**; `Ctrl/Command+Shift+H` opens the window. Explicit Quit checkpoints active transfers as paused. Reopen and Resume to continue. Sleep, logout, shutdown, OS kill and unavailable Tailscale can interrupt work; the next run reconciles confirmed offsets.

The macOS menu-bar icon uses the transparent monochrome [Ribbon Z](../../branding/zing-mark.svg) as an OS template; Linux uses the app icon for contrast on light and dark panels. Regenerate the checked-in 32 px template with `python3 clients/desktop/src-tauri/icons/generate-tray.py` from the project root. This uses Python's standard library and checks the canonical SVG geometry before writing. The launcher uses a white Ribbon Z on navy (`#244C6A`), matching the [user-approved nautical palette](../../branding/README.md) without extra red icon detail. Refresh it by copying the interface owner's matching generated `web/public/icon-512.png` to `clients/desktop/src-tauri/icons/icon.png`. Installed appearance requires release acceptance.

Zing source implements registered devices, immutable send routing and opt-in arrivals. See [release validation](../../docs/validation.md) for current package status. The verified **0.1.1** installers below are historical; their acceptance does not cover later source or packages. Application IDs, private data directories, CLI names, queue compatibility and ad-hoc signing are preserved.

Household builds of **0.1.3** can open the shared feed on first launch without a setup form. The private build supplies `HOUSEHOLD_DEFAULT_ORIGIN`; the native queue saves that validated HTTPS origin, an empty token and the existing **Desktop** device label before the interface reads its configuration. Settings remain available to rename or change the connection. Existing settings, tokens, device identity and queued routing survive upgrades. An explicit Disconnect remains disconnected after relaunch or upgrade, including when no configuration file exists; it never triggers automatic pairing again.

Generic builds with no supplied default retain manual setup: save the household server's Tailscale HTTPS origin and this device's name once. Leave the token empty when the server explicitly uses [Tailscale Serve sign-in](../../docs/api-contract.md#optional-tailscale-serve-sign-in). **Advanced** token entry is for a token-mode server or the configured fallback for tagged Tailscale clients. Every device still needs household Tailscale access; Disconnect only clears local app connection state and does not revoke that access.

## Build from source

Prerequisites must already be installed: a supported Rust toolchain/Cargo, Node + pnpm, and [Tauri platform prerequisites](https://v2.tauri.app/start/prerequisites/) (Xcode command-line tools on macOS; GTK/WebKit and native build packages on Linux). Project package installation below does not install OS toolchains.

From the project root:

```sh
pnpm --dir web install --frozen-lockfile
pnpm --dir clients/desktop install --frozen-lockfile
cargo test --locked --manifest-path clients/desktop/native/Cargo.toml
cargo build --locked --release --manifest-path clients/desktop/native/Cargo.toml
pnpm --dir clients/desktop dev
# Or create a local installed bundle:
pnpm --dir clients/desktop build
```

For a private household build, export `HOUSEHOLD_DEFAULT_ORIGIN` with the household HTTPS origin before compiling **both** the helper and Tauri app. Use only an origin, with no credentials, path other than `/`, query or fragment. The native first-run check rejects invalid defaults before writing configuration or identity. Leave the variable unset or empty for a generic build. Supply the real address through the private build environment; public source contains no household address or token. The compiled address is a connection default, not authentication: the server still requires Tailscale identity or an explicitly configured token. Changing the environment when launching an already compiled app does not change its embedded default.

Tauri invokes the shared web build, then bundles it locally. The installed shell never loads the configured server into a privileged webview. Local app data APIs use the bounded `native_api` bridge, while large transfer bytes remain entirely in Rust. Release CSP permits only native IPC. Native HTTP follows no redirects, attaches the bearer token only to the configured origin, and accepts HTTPS or explicit HTTP loopback. Config paths and transfer locations are origin-checked. No public listener is created.

On macOS, `tauri.conf.json` uses ad-hoc signing (`-`), with no account or notarization requirement. The CLI must be built for the same platform. To install that helper yourself:

```sh
mkdir -p "$HOME/.local/bin"
cp clients/desktop/native/target/release/household-share-cli "$HOME/.local/bin/"
codesign --force --sign - "$HOME/.local/bin/household-share-cli"
```

See `integrations/macos/README.md` for Quick Action/Shortcut capture. The helper is separate from the Tauri app bundle in this source build; there is no automatic system install. Linux users may run the helper from its build location or copy it to their own user bin directory.

## Headless queue and capture

The bundled helper in a private household build uses the same compile-time default on its first file/text capture, even before the GUI has been opened. It saves native config/identity without taking the transfer queue lock; pairing, Disconnect and first-run initialization share a separate config lock so concurrent helper/GUI use cannot overwrite an explicit choice. Saved config and Disconnect take precedence. Generic builds configure once through the app as described above. For token-mode standalone setup, the existing command below reads the configured token from stdin until EOF, never from a CLI argument:

```sh
clients/desktop/native/target/release/household-share-cli configure https://your-box.your-tailnet.ts.net Desktop
```

`household-share-cli enqueue /absolute/path/a /absolute/path/b` durably spools file sources, then starts the installed app in background. `household-share-cli text` streams stdin to a single private staging file before enqueueing it. Capture acknowledgement means **queued locally**, not uploaded. If launching fails, open the app later; the spool survives. Temporary exported files must be saved durably before using file capture. Capture records file size, modification time, inode/device on Unix, and SHA-256 of the first/last 64 KiB quickly. The worker computes and persists a full streaming SHA-256 before the first network upload, and checks that full fingerprint again after process restart before resuming. It checks metadata/sampled content around each subsequent chunk. Full verification runs in the worker, so capture returns quickly; pause/cancel interrupts verification. This source-change protection is separate from end-to-end sender/server digest comparison, which the API does not currently provide.

`household-share-cli run` runs the native worker in a terminal without the UI. Do not run it alongside the GUI: an exclusive per-user lock prevents two processes corrupting the queue. `list` reads redacted transfer views while no queue owner runs. Queue corruption fails visibly rather than discarding resumable state. Credentials and queue files live in the platform's per-user local application-data directory (`ProjectDirs("net","household","HouseholdShare")`), mode 0700 directories/0600 JSON on Unix. Tokens are stored on disk there; OS keychain integration is not implemented.

## Transfer behavior

Uploads use tus creation, HEAD reconciliation, sequential ≤8 MiB PATCH bodies, and termination. The client retains the server/upload URL, item ID, source identity, acknowledged offset, status and server configuration in atomic, synced JSON. Server offset wins after a lost ACK/restart. Creation is saved before sending bytes. An ambiguous upload creation response becomes a visible error requiring inspection rather than an automatic retry that could create a duplicate. A crash between server creation and saving Location can leave an abandoned empty server upload; server-side expiry is the cleanup path. A full tus offset is followed by application item validation: only `ready` becomes complete and permits staged-source cleanup. Pending validation remains `validating`; rejected validation retains the original staged source and an error, including after Resume/restart.

File and text capture bind the intended server before acknowledging the local spool write. Spool messages contain no token. If another server is paired before ingestion, those captures stay paused for their original server; reconnect that server and Resume. Cancel terminates incomplete uploads. If a lost final acknowledgement races with Cancel and tus DELETE returns 409, the client reconciles the item: already-ready content becomes complete and remains shared until explicitly deleted; pending validation retries, and failed validation stays an error.

Downloads issue HEAD, require a strong ETag, fetch bounded byte ranges, validate Content-Range/length/ETag, and sync data before checkpointing. A changed ETag/200 response invalidates the partial rather than appending; explicit Resume starts cleanly. Server `"sha256-<digest>"` ETags are incrementally verified against the entire local file before publication. Resume reconciles actual partial-file length. A private `.household-<id>.part` in the chosen destination directory is published by atomic hard link only when complete; existing destination files are never replaced. The destination filesystem must support hard links (ordinary APFS/ext4 do). Unsupported filesystems report an error and retain the partial for retry. Cancellation removes partial data; interrupted cancellation remains visible/retryable until tus DELETE succeeds. Files are limited to 20 GiB and retain 16 MiB minimum local free space per download step. Text capture also checks available disk space while streaming. Network/HTTP 5xx/429 errors use capped backoff and become visible errors after eight retries; authentication, source, protocol and disk errors require explicit Resume after correction.

One worker processes queued transfers serially with bounded buffers; no full-file in-memory buffering or base64 file transport. Base64 is used only for short tus metadata. A pause/cancel takes effect after the current bounded request, up to the request timeout. Requests time out after 120 seconds, then reconcile before retry. The app window and webview do not own this worker.

Transfer views contain `{id,direction,name,size,offset,status,error,itemId}`. Status is queued/checking/running/validating/paused/cancelling/cancelled/complete/error; size/offset are 64-bit byte counts safely representable at this target. The UI polls the queue and feed. Native API excludes upload/download/event bodies and caps text responses at 8 MiB, metadata responses at 2 MiB, and JSON request bodies at 40 MiB (server defaults to 32 MiB decoded text). Larger stored text should download through the queue. The shared UI bounds expansion separately to 256 KiB; command cancellation is checked between bounded native reads (a stalled read may wait until its request timeout). UI expansion/copy remains explicit and bounded. Native API returns HTTP status/body, including errors; transport errors reject the command. The full common bridge contract and redacted test values are in `clients/shared/native-contract.md` and `native-contract-fixture.json`.

## Devices and arrival notifications

One cryptographically random 32-hex identity per normalized paired server lives outside the WebView in private `devices.json`, shared with CLI/Finder capture under a separate file lock. The UI registers the redacted ID/platform through `native_api`; upload and arrival workers also idempotently register it with `preserveExisting:true`. Background registration never overwrites an existing label/platform with stale queue or configuration metadata; only explicit naming uses the normal upsert. The server’s registered label remains authoritative for new item snapshots. Renaming, upgrading and toggling notifications reuse that ID. Device IDs route attention within the shared household; they are not credentials or access controls. All shares retains everything; For you uses durable server arrival rows independently of notification acknowledgement.

Before a picker or streamed capture starts, `intake/` saves the destination, source ID/label and exact recipient selection without credentials. The same routing enters `inbox/` and `queue.json`, then tus metadata. Switching pairing while the picker is open cannot move the capture; returning to that server and Resume preserves its recipients and source label. Empty/omitted targets means Everyone. Direct helper capture always starts as Everyone. Legacy spool/queue rows without routing remain legacy Everyone sends. An interrupted picker intent alone sends nothing; only an acknowledged spool entry becomes transfer work.

Arrivals start **disabled**. Enable is explicit; disabling does not pause transfers. The independent native thread checks about every 5 seconds, backs off to 60 seconds on failures, serializes processing and handles at most 50 arrivals per cycle in one generic banner. It retains processed progress by origin/device only after confirmed platform handoff, before monotonically acknowledging the returned cursor; ACK leaves For you history intact. Restart retries a lost ACK before fetching subsequent arrivals. A backend error, missing receipt or timeout leaves the page unprocessed, saves a generic settings error and retries with backoff. Disconnect disables arrivals and clears a pending click target while retaining stable device identity and processed progress.

Banners say **Zing — New share available** (or **New shares available**) without sender, filename, text or preview. Notification actions are registered before posting. A click persists only the internal origin/item target, checks the current paired origin and 32-hex item ID, then schedules show/unminimize/focus on Tauri's UI thread. The UI consumes that target after bootstrap, refetches the item, selects For you and handles offline/deleted items. Clicking never downloads, copies or opens a remote URL.

The small `notifications/` adapter replaces the asynchronous notification plugin. It reuses exact, previously locked `zbus =5.19.0` and its existing `async-io =2.6.0` / `futures-lite =2.6.1` primitives on Linux, plus `cc =1.9.0` to build a macOS system `UserNotifications` bridge; no new registry package/version, npm dependency, external push service or runtime framework is added. Linux waits for a nonzero D-Bus `Notify` receipt, with a three-second timeout per call and a separate cancellable three-second connection/authentication limit. Its action subscription uses the sending connection and starts before posting. A retry may replace only its actual server-issued ID for that exact internal batch/target and current unique server owner; hashes never become arbitrary D-Bus replacement IDs. Closed or previous-owner entries are discarded. At most 256 outstanding targets and 512 queued signals are retained; reaching the target limit reports an error and keeps arrivals unprocessed until old alerts close. macOS waits up to three seconds for `addNotificationRequest`'s completion without an error, separately from user interaction. Its retained delegate precedes posting, and only explicit Enable requests authorization (up to 30 seconds); denial leaves the feed and transfers usable. An unavailable center does not prevent startup.

Settings report permission **unknown** because there is no synchronous cross-platform permission/settings query. Stable internal IDs derive from origin/device/sequence. macOS receives an app-scoped request identifier, without a promise to replace an already delivered banner. Confirmed handoff is not OS presentation evidence: notification settings, Do Not Disturb and desktop support can suppress display/actions. OS handoff and persistence are not atomic; a crash or an accepted but timed-out call can duplicate a banner. Linux/macOS actions depend on the resident process; no cold-process launch or delivery after Quit is promised. A click target already persisted by our callback survives restart until consumed. Check real display, lock-screen privacy and click behavior on each desktop.

Close hides the window and retains polling. Explicit Quit, sleep, logout, shutdown, process death or lost Tailscale access stop or delay arrivals; reopening catches up. Neither notification permission nor a saved cursor proves OS presentation. No public listener, automatic download, APNs/Firebase project, developer account or battery exemption is introduced.

For Linux upgrades, `tauri.linux.conf.json` intentionally retains internal productName **Household Share** because the pinned bundler derives Debian `Package` and desktop filename from it. A desktop template shows **Zing** while preserving package `household-share`, launcher `Household Share.desktop`, binary `/usr/bin/household-share` and icon `household-share.png`. The generated DEB filename consequently retains `Household Share_<version>_amd64.deb`; publication may rename the downloadable file without changing its package identity. Verify actual package fields, upgrade replacement and pinned launchers in root's final build. On macOS the product/bundle/volume is **Zing**, the DMG is `Zing_<version>_<arch>.dmg`, and the helper starts it using `open -b net.household.share`; data directories, helper binary and bundle ID remain stable.
